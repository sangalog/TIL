## 📌 오늘 학습한 주제

**Git 6강 — Merge와 Rebase**

## 💡 오늘 배운 것

### 1. merge와 rebase의 차이

브랜치에서 따로 진행한 작업은 나중에 하나로 합칠 수 있다. merge와 rebase는 둘 다 작업을 합치는 방법이지만, 커밋 이력을 연결하는 방식이 다르다.

| 구분 | merge | rebase |
| --- | --- | --- |
| 개념 | 두 브랜치의 작업을 합침 | 내 작업을 다른 브랜치의 마지막 커밋 뒤에 이어 붙임 |
| 이력 모습 | 갈라졌다가 합쳐지는 형태 | 한 줄로 이어지는 형태 |
| 사용 목적 | 브랜치를 나눠 작업한 흔적을 남길 때 | 커밋 이력을 한 줄로 깔끔하게 정리할 때 |

> **rebase는 작업 내용을 없애는 것이 아니라 커밋 이력을 다시 만드는 방식**이다. 다시 만들어진 커밋은 해시값도 바뀐다. 따라서 이미 팀원과 공유한 커밋은 함부로 rebase하지 않는다.

### 2. merge — main에 다른 브랜치의 작업 합치기

`main`에서는 멤버를 추가하고 `add-coach`에서는 코치를 추가한다. 두 작업을 **main에 모으려면 먼저 main으로 이동**한 뒤 병합한다.

```bash
git switch main
git merge add-coach
```

- `main`의 멤버 추가 내용과 `add-coach`의 코치 추가 내용이 함께 반영된다.
- 양쪽에 서로 다른 커밋이 쌓여 있으므로, 두 이력을 이어 주는 **병합 커밋**이 만들어진다.
- 새로운 브랜치가 생기는 것이 아니라, **main에 병합 커밋이 추가되는 것**이다.

**병합 커밋이란?**

병합 커밋은 **부모가 2개인 커밋**이다. 일반 커밋은 바로 앞 커밋 하나만 가리키지만, 병합 커밋은 합쳐진 두 브랜치의 끝을 동시에 가리킨다.

```
        A ── B ── M   ← main (M이 병합 커밋)
       /         /
 ... ─ O        /
       \       /
        C ── D        ← add-coach
```

- A, B는 main에서 멤버를 추가한 커밋이고, C, D는 add-coach에서 코치를 추가한 커밋이다.
- M은 "B와 D를 합쳤다"는 연결 기록이며, 부모가 B와 D이다.
- 메시지는 `Merge branch 'add-coach'`처럼 자동으로 만들어진다. 그래서 병합할 때 커밋 메시지 편집기가 열린다.

커밋 메시지 편집기로 Vim이 열리면 `Esc` → `:wq` → `Enter`로 저장하고 종료한다.

**병합을 끝낸 브랜치 정리하기**

```bash
git branch -d add-coach
git branch
```

더 이상 사용하지 않을 브랜치는 삭제할 수 있다. **브랜치를 삭제해도 main에 합쳐진 작업과 이력은 남는다.** 삭제는 필수가 아니라 작업이 끝난 가지를 정리하는 과정이다.

> 병합 전 커밋의 해시값으로 `git reset --hard 커밋해시`를 실행하면 병합 전으로 되돌릴 수 있다. 아직 커밋하지 않은 수정 내용이 사라질 수 있고, 이미 공유한 이력을 되돌릴 때는 팀원에게 미칠 영향도 확인해야 한다.

### 3. rebase — 내 작업을 main의 끝에 이어 붙이기

`new-teams` 브랜치에는 새로운 팀 파일을 추가한 커밋(D, E)이 있다. 그런데 그사이 main에는 새 커밋(C)이 생겨서 두 브랜치의 이력이 갈라진 상태이다.

```
rebase 전

A ── B ── C          ← main
      \
       D ── E        ← new-teams
```

이 작업들을 최신 main 뒤에 이어 붙이려면 **작업을 옮길 new-teams로 이동**한 뒤 rebase한다.

```bash
git switch new-teams
git rebase main
```

- `main`의 최신 커밋 C를 새로운 출발점으로 삼는다.
- 그 뒤에 `new-teams`의 커밋들이 다시 만들어져 이어진다. D′, E′는 기존 D, E의 작업을 다시 적용해 만든 커밋이다.
- **new-teams는 갱신되지만, main의 위치는 그대로이다.**

```
rebase 후

A ── B ── C ── D ── E
          ↑          ↑
        main     new-teams
```

| 브랜치 | 가리키는 위치 |
| --- | --- |
| `main` | C |
| `new-teams` | C 뒤에 이어진 D′ → E′ 중 마지막 E′ |

### 4. rebase 후 main도 앞으로 이동시키기

**rebase만으로 main에 새 팀 작업까지 반영되는 것은 아니다.** main으로 돌아와 `new-teams`를 합친다.

```bash
git switch main
git merge new-teams
```

main이 가리키는 C부터 new-teams의 E′까지 커밋이 한 줄로 이어져 있어, **새 병합 커밋을 만들지 않고 main의 위치만 E′로 앞으로 옮겼다.** 이렇게 브랜치의 위치만 앞으로 이동하는 방식을 **Fast-forward**라고 한다.

```
merge 후

A ── B ── C ── D ── E
                     ↑
              main, new-teams
```

| 구분 | 실행 전 | 실행 후 |
| --- | --- | --- |
| `main`의 위치 | C | E |
| main에서 볼 수 있는 내용 | 기존 작업 | 기존 작업 + 새 팀 추가 작업 |

이 경우에는 main의 위치만 앞으로 옮기면 되므로, **두 브랜치의 작업을 합친 결과를 기록하는 ‘병합 커밋’** 을 새로 만들 필요가 없다. 즉, merge가 항상 병합 커밋을 만드는 것은 아니다.

작업이 끝난 브랜치는 main에서 삭제한다.

```bash
git branch -d new-teams
```

> **merge는 합칠 내용을 받을 브랜치에서, rebase는 커밋을 옮길 브랜치에서 실행한다.** 

## 🔄 흐름 요약

| 방식 | 순서 |
| --- | --- |
| merge | main으로 이동 → add-coach 병합 → 결과 확인 → add-coach 삭제 |
| rebase 후 통합 | new-teams로 이동 → main 기준으로 rebase → main으로 이동 → new-teams를 merge하여 Fast-forward → new-teams 삭제 |

SourceTree를 새로고침하면 커밋이 연결된 모습과 각 브랜치의 위치를 확인할 수 있다. 

## ✍️ 내가 이해한 핵심

두 방식 모두 작업을 합치는 데 쓰이지만, merge는 분기된 이력을 유지하고 rebase는 내 커밋을 새 기준 뒤에 다시 연결한다는 차이가 있었다. 특히 **rebase 후에도 main은 그대로이므로, main으로 이동해 merge하는 과정이 필요했다는 점**을 기억해야겠다. 앞으로는 명령어를 실행하기 전에 현재 브랜치와 작업을 합칠 방향을 먼저 확인해야겠다.
