**Java 6강 — 클래스와 인스턴스**

## 💡 오늘 배운 것

### 1. 클래스와 인스턴스 다시 이해하기

클래스는 **객체를 만들기 위한 설계도**이고, 인스턴스는 **그 설계도로 만든 실제 객체**다.

예를 들어 `Member`라는 설계도로 홍길동 회원과 김철수 회원을 각각 만들 수 있다.

```java
class Member {
    String name;                         // 회원마다 따로 가지는 이름
    static String serviceName = "회원 서비스"; // 모든 회원이 함께 사용하는 값
}
```

이 설계도로 객체를 만들어 보자.

```java
Member member1 = new Member();
member1.name = "홍길동";

Member member2 = new Member();
member2.name = "김철수";
```

| 코드 | 의미 |
| --- | --- |
| `Member` | 회원 객체의 설계도이자 변수의 타입 |
| `new Member()` | 새로운 회원 객체 생성 |
| `member1`, `member2` | 각각 생성된 회원 객체를 가리키는 변수 |
| `member1.name` | member1이 가리키는 회원의 이름 |
| `member2.name` | member2가 가리키는 회원의 이름 |

`member1`과 `member2`에는 객체 자체가 아니라 **어떤 객체를 사용할지 가리키는 정보인 참조**가 담긴다. 이처럼 객체의 참조를 담는 변수의 타입으로 사용할 수 있어서, 클래스를 **참조 타입**이라고 한다.

**그렇다면 ‘객체에 속한다’와 ‘클래스에 속한다’는 어떻게 다를까?**

클래스 안에 정의한 변수나 메서드를 **멤버**라고 한다. 멤버는 `static` 여부에 따라 구분한다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| **인스턴스 변수** | 객체마다 각각 가지는 값 | 회원마다 다른 `name` |
| **static 변수** | 클래스에 하나만 두고 함께 사용하는 값 | 공통으로 사용하는 `serviceName` |

```java
System.out.println(member1.name);      // 홍길동
System.out.println(member2.name);      // 김철수

System.out.println(Member.serviceName); // 회원 서비스
```

`name`은 **어느 회원의 이름인지** 알아야 하므로 객체를 가리키는 변수로 접근한다. 반면 `serviceName`은 특정 회원의 정보가 아니므로 **객체를 만들지 않고 클래스 이름으로 접근**할 수 있다.

메서드도 마찬가지로, 인스턴스 메서드는 객체를 통해 호출하고 `static` 메서드는 객체 생성 없이 클래스 이름으로 호출할 수 있다.

> **인스턴스 멤버는 각 객체를 기준으로 사용하고, static 멤버는 클래스를 기준으로 사용한다.**

### 2. 클래스를 프로젝트 구조로 확장하기

웹 애플리케이션에서는 여러 클래스가 협력해 요청을 처리한다. Spring은 이런 애플리케이션 개발을 지원하고, **Spring MVC**는 MVC(Model·View·Controller) 패턴을 바탕으로 웹 요청·응답 처리를 돕는다.

클래스가 많아지면 **역할에 맞게 나누고, 관련된 클래스를 묶어 관리**해야 한다. 이때 사용하는 개념이 `package`와 `import`다.

### 3. 클래스 이름으로 역할 구분하기

| 클래스 역할 | 담당하는 일 | 회원 가입 예시 |
| --- | --- | --- |
| **Controller** | 요청을 받고 서비스를 호출해 응답 | 가입 정보를 받아 Service에 전달 |
| **Service** | 비즈니스 로직, 즉 업무 규칙 처리 | 중복 가입 여부 판단 |
| **Repository / DAO** | 데이터 저장·조회 등 데이터 접근 | 기존 회원 조회, 새 회원 저장 |

Controller를 흐름을 조율하는 역할로 본다면, Service는 실제 업무를 처리하고 Repository·DAO는 데이터 접근을 담당한다.

- **비즈니스 로직**: ‘같은 이메일로 중복 가입할 수 없다’ 같은 업무 규칙
- **영속성**: 프로그램이 종료돼도 데이터가 유지되는 성질. 보통 DB에 저장해 확보한다.
- **ServiceImpl**: 보통 서비스 인터페이스를 구현한 클래스에 붙이는 이름

Repository와 DAO는 세부 설계 개념은 다르지만, 여기서는 **데이터 접근 작업을 분리하는 역할**을 중심으로 이해한다.

**데이터를 담는 객체도 역할이 다르다.**

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| **DTO** — Data Transfer Object | 계층 사이 또는 요청·응답에서 데이터를 전달하는 객체 | 가입 요청 정보 |
| **VO** — Value Object | 값 자체로 의미를 갖는 객체. 보통 불변으로 설계 | 금액, 주소 |
| **Entity** | 식별자로 구분되는 객체. JPA에서는 DB 테이블과 매핑 | 회원 ID로 구분하는 회원 |

DTO에는 가입 요청의 이름·이메일이나 조회 응답의 회원 정보를 담을 수 있다. **DTO·Entity에 데이터를 담는 것과 Repository·DAO가 DB에 접근하는 것은 서로 다른 역할**이다.

### 4. package와 import로 클래스 관리하기

문서를 폴더별로 정리하듯, 관련된 클래스를 **패키지(package)** 로 묶는다. 클래스를 찾기 쉬워지고, 이름이 같은 클래스도 패키지로 구분할 수 있다.

- `package`: 클래스가 속한 패키지를 선언한다.
- `import`: 다른 패키지의 타입을 전체 이름 대신 짧은 이름으로 사용할 수 있게 한다.

```java
package test.controller;

import test.service.TestService;

public class TestController {
    private TestService service;
}
```

> **import나 변수 선언만으로 객체가 생성되는 것은 아니다.** 같은 패키지의 타입은 보통 import 없이 사용하며, import가 접근 제한을 없애 주지는 않는다.

**역할에 따른 패키지 구성 예시**

| 패키지 | 클래스 예시 |
| --- | --- |
| `test.controller` | `TestController` |
| `test.service` | `TestService` |
| `test.repository` | `TestRepository` |
| `test.domain.dto` | `TestRequestDto`, `TestResponseDto` |
| `test.domain.entity` | `TestEntity` |

패키지 이름의 점(`.`)은 보통 디렉토리 구조에 대응한다. 예를 들어 `test.service`는 소스 폴더 아래 `test/service` 경로에 둔다.

**도메인**은 회원·주문·게시글처럼 프로그램이 다루는 업무 영역이다. 회원 관련 코드를 `member` 아래에 모으고, 그 안에서 역할별 패키지를 나눌 수도 있다.

### 5. 백엔드의 요청·응답 흐름 이해하기

Controller·Service·Repository는 책임에 따라 나눈 **논리적인 계층**이다. 각각 별도 서버가 있어야 한다는 뜻은 아니다.

회원 조회 요청은 다음과 같이 처리할 수 있다.

1. **프론트엔드**가 회원 조회를 요청한다.
2. **Controller**가 요청을 받아 Service를 호출한다.
3. **Service**가 필요한 업무 처리를 하며 Repository에 조회를 요청한다.
4. **Repository**가 DB에서 회원 정보를 조회한다.
5. 처리 결과를 응답 DTO 등에 담아 **JSON으로 프론트엔드에 전달**한다.

> **Controller는 요청·응답, Service는 업무 처리, Repository는 데이터 접근을 담당한다.** 이 계층 구분을 MVC의 세 요소와 같은 것으로 보면 안 된다.

데이터 접근을 위한 기술에는 JPA와 MyBatis 등이 있다.

| 기술 | 핵심 역할 |
| --- | --- |
| **JPA** | 자바 객체와 관계형 DB를 매핑하는 ORM 표준. Hibernate 같은 구현체를 사용 |
| **MyBatis** | 직접 작성한 SQL과 자바 객체 사이의 매핑 지원 |

**DTO는 MyBatis 전용이 아니며 JPA에서도 사용한다.** Repository·DAO라는 이름 역시 특정 기술에만 사용하는 것은 아니다.

요청과 응답에 필요한 정보가 다르면 `TestRequestDto`, `TestResponseDto`처럼 나눈다. 예를 들어 가입 요청으로 받은 비밀번호를 응답에 그대로 담지 않도록 구성할 수 있다.

### 6. 클래스끼리 협력하려면 의존 관계가 필요하다

Controller가 Service의 기능을 사용하면 **Controller가 Service에 의존한다**고 한다. Service가 Repository를 사용하는 것도 같은 관계다.

```java
public class TestController {
    private TestService service = new TestService();
}
```

Controller 안에서 `new TestService()`로 객체를 만들고, 그 참조를 `service` 변수에 저장했다. 이후 `service`를 통해 접근 가능한 Service의 메서드를 호출할 수 있다.

Service도 같은 방식으로 Repository 객체를 사용해 데이터 조회·저장 작업을 요청할 수 있다.

> **의존 관계는 필요한 기능을 다른 객체에 맡겨 사용하는 관계다.** 위 코드는 객체를 직접 생성하는 방식이며, 외부에서 객체를 전달받는 의존성 주입(DI)과는 구분한다.

### 7. 높은 응집도와 낮은 결합도 지향하기

| 개념 | 의미 | 설계 방향 |
| --- | --- | --- |
| **응집도(Cohesion)** | 클래스 내부 기능들이 하나의 책임에 얼마나 밀접하게 모여 있는가 | 자기 역할에 집중하도록 높게 유지 |
| **결합도(Coupling)** | 다른 클래스에 얼마나 강하게 의존하는가 | 변경 영향이 불필요하게 퍼지지 않도록 낮게 유지 |

예를 들어 DB 접근 방식이 바뀌더라도 Controller까지 수정할 필요가 없도록 책임과 연결 방식을 설계한다.

> **각 클래스는 자기 역할에 집중하고, 필요한 기능은 다른 클래스와 협력해 처리한다.**
