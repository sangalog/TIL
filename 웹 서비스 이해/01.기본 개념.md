## 📌 오늘 학습한 주제

**웹 서비스 이해 1강 — 기본 개념**

웹 서비스를 이루는 영역과 요청·응답의 흐름을 이해한다. 지금은 코드를 구현하기보다 **각 용어가 어디에 쓰이는지 연결해서 생각하는 것**이 목표다.

## 💡 오늘 배운 것

### 1. 웹 서비스의 큰 그림

웹 서비스는 **클라이언트가 요청하고, 서버가 처리한 결과를 응답하는 구조**다.

**사용자 → 프론트엔드(FE) → 백엔드(BE) → 필요하면 DB 접근**<br>
**처리 결과 → 프론트엔드 → 사용자에게 표시**

| 구분 | 역할 |
|---|---|
| **클라이언트** | 사용자를 대신해 서비스를 요청하는 브라우저나 앱 |
| **프론트엔드** | 사용자가 클릭하고 입력하며 결과를 확인하는 화면과 동작 |
| **백엔드** | 전달받은 요청을 업무 규칙에 맞게 처리하는 서버 영역 |
| **DB** | 회원 정보·게시글처럼 계속 보관해야 하는 데이터를 저장하는 창고 |

사용자가 컴퓨터를 다룰 때 운영체제의 도움을 받는 것처럼, 웹에서는 **화면(UI)을 통해 원하는 기능을 요청한다.** 일반적인 웹 서비스에서 사용자가 DB를 직접 조작하는 대신, 백엔드가 필요한 데이터에 접근한다.

> **영속성**은 데이터를 일시적으로 쓰고 버리는 것이 아니라, 저장해 두고 나중에도 사용할 수 있는 성질이다.

### 2. 서비스 구조의 기본 흐름

**로그인 버튼을 누르는 상황**으로 생각하면 쉽다.

1. **사용자 입력**: 화면에서 아이디·비밀번호를 입력하고 로그인 버튼을 누른다.
2. **요청(Request)**: 브라우저가 로그인에 필요한 데이터를 서버로 보낸다.
3. **서버 처리**: 백엔드가 입력값과 회원 정보를 확인한다. 필요하면 DB를 조회한다.
4. **응답(Response)**: 서버가 로그인 성공 여부 등의 결과를 돌려준다.
5. **화면 표시**: 프론트엔드가 결과에 따라 화면을 이동하거나 안내 문구를 보여준다.

버튼 클릭이나 입력 같은 동작을 **이벤트(Event)** 라고 한다. 서버 처리가 필요한 이벤트는 요청으로 이어지지만, 메뉴를 펼치는 것처럼 화면 안에서만 처리할 수도 있다.

### 3. 개발자의 역할과 진로

전체 서비스를 혼자 개발해야 하는 것은 아니다. 각 영역을 나누어 담당하며 협업할 수 있다.

| 분야 | 역할 |
|---|---|
| **프론트엔드(FE)** | 화면과 상호작용을 구현하고 사용하기 편하게 만든다. |
| **백엔드(BE)** | 업무 로직, 권한 확인, 데이터 조회·저장 등을 구현한다. |
| **DBA** | DB를 안정적으로 운영하고 성능·보안·백업 등을 관리한다. |
| **풀스택** | 프론트엔드와 백엔드를 아우르고 필요한 DB 작업도 다룬다. |
| **DevOps** | 개발과 운영을 연결해 배포·자동화·안정적인 서비스 운영을 돕는다. |

- **UI(User Interface)**: 버튼·입력창·메뉴처럼 사용자가 접하는 화면과 조작 요소
- **UX(User Experience)**: 서비스를 이용하며 느끼는 편리함과 전체 경험
- **DBA(Database Administrator)**: 데이터베이스 관리자. 단순히 데이터를 저장하는 역할보다 운영·관리의 범위가 넓다.
- **배포**: 개발한 프로그램을 사용자가 이용할 수 있는 환경에 올려 실행하는 작업

> 프론트엔드에도 입력 검증이나 화면 상태를 다루는 로직이 있다. 중요한 업무 규칙과 권한 검사는 백엔드에서 검증한다.

### 4. API: 서로 맞춰야 하는 요청·응답의 약속

**API(Application Programming Interface)** 는 다른 프로그램의 기능을 사용할 수 있게 제공하는 인터페이스다. 웹 개발에서는 **어디로 어떤 데이터를 보내고, 어떤 결과를 받을지 정한 접점**으로 이해하면 쉽다.

예를 들어 회원 조회 기능을 함께 개발한다면 다음을 맞춰야 한다.

| 미리 정할 것 | 예시 |
|---|---|
| 요청 방법과 주소 | `GET /users/1`로 1번 회원 조회 |
| 응답 형식 | JSON으로 회원 번호와 이름 반환 |
| 오류 처리 | 회원이 없을 때 보낼 상태 코드와 안내 내용 |

- **엔드포인트**: API 요청을 보내는 주소나 경로
- **JSON**: 웹 API에서 자주 사용하는 데이터 표현 형식
- **API 명세서**: 요청 방법·경로·입력값·응답 등을 정리한 문서
- **Swagger**: API 설계와 문서화를 돕는 도구 모음. Swagger UI로 명세를 확인하고 요청을 실행해 볼 수 있다.

**명세를 먼저 맞추면 프론트엔드와 백엔드가 따로 개발해도 결과를 연결하기 쉽다.** 개발자와 기획자 모두 같은 문서를 보며 소통할 수 있어, 데이터 형식 차이와 통합 오류를 줄일 수 있다.

### 5. 기획과 연결해서 생각하기

- **프론트엔드**: 사용자가 어떤 화면에서 무엇을 입력하고 확인할까?
- **백엔드**: 어떤 조건과 규칙으로 요청을 처리할까?
- **DB**: 어떤 정보를 저장하고, 데이터끼리 어떤 관계가 있을까?
- **API**: 어떤 요청을 보내고 어떤 결과를 받을까?

## 🔄 흐름 요약

**사용자 입력 → 요청(Request) → 서버 처리 → 응답(Response) → 화면 표시**

1. 사용자가 프론트엔드에서 클릭하거나 입력한다.
2. 서버 처리가 필요하면 브라우저가 백엔드로 요청을 보낸다.
3. 백엔드는 업무 로직을 처리하고, 필요하면 DB를 조회하거나 변경한다.
4. 서버가 결과를 응답하면 프론트엔드가 사용자에게 보여준다.
   
## ✨ 내가 이해한 핵심

**프론트엔드는 사용자와 연결하고, 백엔드는 요청을 처리하며, DB는 데이터를 보관한다.** 이 영역들이 함께 움직이려면 요청과 응답의 흐름을 이해하고, API 명세로 서로의 약속을 맞춰야 한다.
